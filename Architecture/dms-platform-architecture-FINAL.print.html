MySQL → PostgreSQL — it is a SPLIT, not a copy

One MySQL database of ~240 tables becomes ten PostgreSQL service databases, each with a t_<temple> schema, with type conversion along the way.
1. pgloader lands a faithful, type-converted copy of one temple's MySQL database into a staging schema
2. Per-service jobs populate each service database from staging
3. Rehearsed in UAT and run repeatedly until it is boring
4. Big-bang cutover per temple; MySQL kept read-only as the rollback

🔴 Reconciliation — the release gate

No temple goes live until this passes:
· row counts match per table
· sum of donation amounts matches to the paisa
· receipt-number sequences continuous, no gaps
· spot-check of donor PII fields
_Given the August 2026 data gap and the 1366 fundraiser_id silent write losses, a migration that "looks fine" is not evidence._

Tenant onboarding — automated

1. Registry row created
2. Shard chosen (join a pool, or open a silo)
3. CREATE SCHEMA t_<temple> in all service databases
4. Flyway fan-out for that schema
5. Seed catalog + settings
6. Keycloak: temple group + first admin
7. DNS record + cert-manager certificate
8. Smoke test → mark active
At 100 tenants this cannot be manual.

Decisions locked

Backend Java 25 LTS · Maven · Spring Boot microservices · Spring Data JPA (CRUD) + jOOQ (reporting) · JobRunr · Flyway
Orchestration k3s, self-hosted, single node on t4g (Graviton). $0 control plane. Kubernetes from day one, so there is no future migration; EKS later = pointing kubectl elsewhere.
Deployment Flux (GitOps). The cluster pulls from git and self-heals drift. Jenkins builds and pushes images, updates the manifest tag, and never holds cluster credentials.
Secrets SOPS + age, encrypted in git, decrypted by Flux.
Data Model D (bridge), built D-minimal. Two shards in every environment from day one. Prod day-1: shard-noida (silo) + shard-pool-1 (GNW, NEX, WHF).
Front door Traefik for TLS and host routing; Spring Cloud Gateway behind it for JWT, temple resolution and rate limits.
Authorization Keycloak carries identity, temple memberships and a coarse role per temple; services enforce fine-grained permissions, cached per request.
Comms REST for synchronous answers + RabbitMQ, in-cluster, published via transactional outbox. /api/v1/, additive-only.
Web One Vite + React + TypeScript SPA (public + admin) · Ant Design · TanStack Query + Zustand · nginx container + CloudFront · per-temple domains, admin and public on the same domain, as today.
Android One Expo app for staff, fundraisers and donors, role-driven from the backend · expo-router · read-only offline cache · FCM direct · replaces fundraiser-app.
Observability Application logs → CloudWatch (JSON, 14-day retention); metrics → in-cluster Prometheus + Grafana; tracing deferred.
Repos One per service (~18 total) + platform-commons + clients + manifests + infra.
Cross-temple screens: NONE. Every screen is one temple. No data warehouse. Verified: today's PHP app has zero DB::connection() calls and one set of DB credentials — it already cannot read another temple.
Audit & activity logs stay inside the temple's own schema. Audit is a library, not a service.
Migration pgloader → staging → per-service split jobs; big-bang per temple; UAT → GNW/NEX → WHF → Noida last.
AI ISKCON-GPT is the single AI platform — Python/FastAPI, running on on-prem GPU hardware, outside AWS. It both serves the platform and reads platform data via /api/v1. Hardware sizing is advisory; nothing is bought and eight assumptions are unconfirmed. The on-prem↔cloud link is still open.

The two irreversible precautions

🔴 No cross-temple SQL
🔴 No cross-temple foreign keys
Two shards make both physically impossible.

k3s operating rules

1. All manifests in git — Flux makes this a mechanism, not a habit
2. Upgrade k3s once a year — the same restart renews its internal TLS certificates
3. AWS permissions: narrow shared node role now → OIDC-based per-service roles (IRSA-style) before the first temple goes live. Never long-lived access keys
4. ECR pulls need a containerd credential helper or a token-refresh CronJob
5. Rehearse the node rebuild in UAT — single-node prod makes rebuild time the real availability number
6. Back up the age key to the password manager

Supporting precautions

🟠 Registry resolves temple → host; no hard-coded DB URLs
🟠 Datasources lazy, cached, refreshable without restart
🟠 Migration fan-out driven by the registry, grouped by shard
🟠 Temple context on every service hop and every async job
🟡 Database names constant across shards; only host varies
🟡 Uniform schema naming t_<temple>
🟡 SET LOCAL, never session SET
🟡 Per-schema dump/restore tooling, tested
🟡 Pool sizes configured per shard
🟡 Registry cache TTL + invalidation

Deliberately NOT in this architecture

so none of it gets re-proposed
❌ Data warehouse / cross-temple queries
❌ Kafka — RabbitMQ chosen; the outbox is the replay log
❌ Amazon MQ — the outbox already de-risks what it would buy
❌ EKS · ECS · Docker Compose in production
❌ ArgoCD — ~1 GB for a UI; Flux gives the mechanism
❌ A two-node cluster — that is not HA; real HA is three servers
❌ Database-per-temple (Model A) — 8,000 connections
❌ Shared schema + tenant_id (Model C) — one missing WHERE leaks donor PII
❌ Long-lived AWS access keys
❌ Server-side rendering / Next.js — no Open Graph tags or SEO in use today
❌ AWS DMS — CDC buys nothing for a big-bang cutover of 2.95 GB
❌ A separate Time Management app, API, domain or deploy

Backup & disaster recovery

· RDS automated backups, 30-day retention + PITR, on every shard
· Weekly pg_dump per t_<temple> schema → versioned S3 bucket with a lifecycle rule
· S3 versioning on from bucket creation
· ⚠️ RDS encryption at rest must be enabled at instance creation — it cannot be added afterwards
· The cluster needs no backup: manifests and secrets are in git, data is in RDS
🔴 Quarterly restore drill in UAT — restore one temple's schema, and rebuild the k3s node from scratch.
An untested backup is not a backup.

Observability

Application logs → CloudWatch Logs — JSON on stdout, 14-day retention, ~$5/mo. This retires the Jenkinsfile's SSH-and-grep check for SQLSTATE errors.
Metrics — Spring Actuator → in-cluster Prometheus + Grafana (~450 MB).
Every log line and metric tagged tenant_id — this is where all-temple questions get answered.
Tracing deferred until service count justifies it.
Verified today: only host metrics (CWAgent) and RDS logs reach CloudWatch; application logs sit on container disks.
